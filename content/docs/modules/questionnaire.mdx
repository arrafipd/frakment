Questionnaire is a **composition**, not a primitive. It wraps a headless engine in `lib/questionnaire` with four Frakment primitives — **Checkbox**, **RadioGroup**, **Button**, and **Card** — to render a multi-step form with navigation, validation, and keyboard shortcuts.

Because the engine is compiled, install it through the CLI, not by copying source. The wrapper is available to copy from the Manual tab below.

## Usage

Import the wrapper from `components/ui/questionnaire` and the engine types from `lib/questionnaire` if you need to type `onStatusChange`.

```tsx title="questionnaire.tsx"
import {
  Questionnaire,
  QuestionnaireActions,
  QuestionnaireChoice,
  QuestionnaireChoices,
  QuestionnaireDescription,
  QuestionnaireError,
  QuestionnaireItem,
  QuestionnaireNext,
  QuestionnairePrevious,
  QuestionnaireProgress,
  QuestionnaireSubmit,
  QuestionnaireTitle,
} from "@/components/ui/questionnaire";
```

```tsx title="questionnaire.tsx"
<Questionnaire items={items} defaultItem="scope" onSubmit={handleSubmit}>
  <QuestionnaireProgress />
  <QuestionnaireItem name="scope" required>
    <QuestionnaireTitle>What should the agent change?</QuestionnaireTitle>
    <QuestionnaireDescription>Pick the change scope.</QuestionnaireDescription>
    <QuestionnaireChoices>
      <QuestionnaireChoice value="component">Component only</QuestionnaireChoice>
      <QuestionnaireChoice value="feature">Complete feature</QuestionnaireChoice>
    </QuestionnaireChoices>
    <QuestionnaireError />
  </QuestionnaireItem>
  <QuestionnaireActions>
    <QuestionnairePrevious />
    <QuestionnaireNext>Next</QuestionnaireNext>
    <QuestionnaireSubmit>Save</QuestionnaireSubmit>
  </QuestionnaireActions>
</Questionnaire>
```

The engine handles keyboard navigation, focus management, and form submission. Every choice renders as a native `<input>` wrapped by **Checkbox** or **RadioGroup** depending on whether the parent item is `multiple`.

## Anatomy

```tsx title="questionnaire.tsx"
<Questionnaire items={items} defaultItem="first">
  <QuestionnaireProgress />
  <QuestionnaireItem name="first" required>
    <QuestionnaireTitle />
    <QuestionnaireDescription />
    <QuestionnaireChoices>
      <QuestionnaireChoice value="a" />
      <QuestionnaireChoice value="b" />
      <QuestionnaireInput />
    </QuestionnaireChoices>
    <QuestionnaireError />
  </QuestionnaireItem>
  <QuestionnaireActions>
    <QuestionnairePrevious />
    <QuestionnaireSkip />
    <QuestionnaireNext />
    <QuestionnaireSubmit />
  </QuestionnaireActions>
</Questionnaire>
```

- **Questionnaire** — form root, tracks current step, focuses the active fieldset
- **Progress** — current position indicator, supports custom `render`
- **Item** — one question; renders as a `fieldset` with a `legend`
- **Title / Description** — question heading and helper text
- **Choices / Choice** — radio or checkbox group, depending on `multiple`
- **Input** — freeform text input inside the choice group
- **Error** — inline error region, wired via `aria-describedby` when invalid
- **Actions / Previous / Skip / Next / Submit** — navigation controls

## Accessibility

- Each `QuestionnaireItem` renders a `fieldset` with `legend` (via `QuestionnaireTitle`), so screen readers announce the question on focus.
- `QuestionnaireError` is linked to the fieldset via `aria-describedby` when the item is invalid.
- Keyboard shortcuts do not replace tab navigation. Users can still move between choices with Tab and Space.
- When the questionnaire is embedded in a Dialog, focus is trapped inside and restored on close.

## Best Practices

- **One question per step.** Long forms break focus management and lose the progress indicator's value.
- **Mark required fields explicitly.** `required` on the item enables inline validation; skipping is only allowed when the field is optional.
- **Use `shortcuts` sparingly.** Letters or numbers help power users in dense flows but confuse others in short flows.
- **Validate on submit, not on every keystroke.** Reserve `invalid` for real problems; show it only after the user tries to advance.
- **Persist answers if the flow spans sessions.** Store `FormData` after each submit; the engine resumes from the active step on load.
- **Keep the last step informational.** The final submit should confirm what will happen, not add a new question.
